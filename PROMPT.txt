# PROJECT PROMPT: AI-POWERED WHATSAPP E-COMMERCE MANAGEMENT PLATFORM

## 1. Project Overview

Design and develop a complete AI-powered e-commerce management platform that allows customers to discover products, receive recommendations, place orders, and interact with a shop through WhatsApp.

The platform must also provide shop administrators with two ways to manage business operations:

1. A web-based administration dashboard accessible through a computer browser.
2. A WhatsApp-based administration interface that allows authorized administrators to manage the shop through conversational commands.

Both interfaces must communicate with the same backend and database to ensure that business information remains synchronized.

The platform must use a **single centralized AI agent** powered by an external language model API. The agent must support two operating contexts:

- Customer Context: Handles shopping-related conversations.
- Admin Context: Handles authorized business management operations.

These are two contexts of the same agent, not separate AI agents.

The application should be modular, secure, maintainable, responsive, and optimized to run on a low-resource Ubuntu VPS with approximately 1 GB RAM.

Customer: "I like the second pair. Add size 42 to my cart."

# 3. Single AI Agent Architecture

Implement one centralized AI agent that communicates with an external model API.

The agent must support two contexts.

### Customer Context

Responsible for:
- Product discovery.
- Product search.
- Recommendations.
- Product questions.
- Cart assistance.
- Order assistance.
- Customer support.

### Admin Context

Responsible for:
- Sales reporting.
- Inventory lookup.
- Product updates.
- Stock adjustments.
- Order management.
- Customer lookup.
- Administrative reporting.
- Notifications.

### Permission-Aware Tool Registry

The AI agent must not have unrestricted database access.

Implement a tool registry that exposes controlled backend operations.

Every tool invocation must pass through validation that checks:

1. User identity.
2. User role.
3. Tool permissions.
4. Input parameter validity.
5. Business rules.
6. Confirmation requirements for sensitive actions.

The tool registry should include:

| Tool | Purpose |
|---|---|
| Product Search | Search the product catalogue |
| Inventory Lookup | Retrieve available stock |
| Cart Management | Add, remove and update cart items |
| Order Management | Create, retrieve and update orders |
| Sales Reporting | Generate business reports |
| Customer Lookup | Retrieve customer information |
| Stock Adjustment | Update inventory quantities |
| Notifications | Send customer and admin notifications |

The agent should request tool execution through the backend. The backend must validate and execute the requested operation before returning the result to the model.

### AI Usage Optimization

Because the platform uses an external model API:

- Store API credentials securely on the server.
- Never expose API keys to the frontend or WhatsApp.
- Track input and output token consumption.
- Monitor estimated API costs.
- Limit conversation history.
- Summarize older conversations when necessary.
- Limit tool execution iterations.
- Use timeouts and error handling.
- Avoid unnecessary model calls.
- Use deterministic backend logic for calculations, payments, stock checks, and order state changes.

The AI should interpret natural language and coordinate tools, not independently determine authoritative business data.

# 4. WhatsApp Integration

Integrate the official Meta WhatsApp Cloud API.

Implement:

- Webhook verification.
- Incoming message processing.
- Outgoing message delivery.
- Customer identification.
- Administrator identification.
- Message status handling.
- Image and document message support where appropriate.
- Interactive WhatsApp messages where supported.
- Error handling.
- Conversation management.

### Message Processing Flow

1. A user sends a WhatsApp message.
2. Meta forwards the message to the application's webhook.
3. The backend verifies the webhook request.
4. The backend identifies the sender.
5. The system determines whether the sender is a customer or administrator.
6. The appropriate context is loaded.
7. The AI agent interprets the message.
8. The agent requests tools when necessary.
9. The permission-aware registry validates each tool request.
10. Backend business services execute authorized operations.
11. The result is returned to the agent.
12. The agent generates a response.
13. The response is sent to WhatsApp.

Administrators must be registered and authenticated. Do not treat possession of a phone number alone as sufficient authorization for sensitive administrative actions.

# 5. Technical Architecture

Use a modular monolithic architecture rather than microservices.

The platform should have clear separation between presentation, application logic, business services, AI orchestration, security, and data persistence.

### Backend

- Python.

- SQLAlchemy.
- Alembic.

- Pydantic.

Organize the backend into independent functional modules:

- Authentication and authorization.
- User management.
- Customer management.
- Product catalogue.
- Categories.
- Inventory.
- Shopping carts.
- Orders.
- Payments.
- WhatsApp integration.
- AI orchestration.

### Frontend

- User-role assignments.
- Customers.
- Categories.
- Products.
- Product variants.

- Order items.
- Payments.

- Notifications.

# 6. Payment and Order Processing

Implement a payment architecture that can support payment providers through external APIs.

Allow payment methods to be configured according to the shop's operating market.

Potential payment options include:
- Mobile money.
- Bank cards.
- Bank transfers.
- Cash on delivery or collection.

Payment processing must be separate from order creation.

An order should not be marked as paid simply because a customer initiated checkout.

Implement:
- Payment initiation.
- Payment references.
- Payment status tracking.
- Verified payment webhooks.
- Idempotent payment event processing.
- Failed payment handling.
- Refund status tracking where supported.

Never store customers' card details or mobile money PINs.

### Order Lifecycle

Use clearly defined order states:

- Pending Payment.
- Paid.
- Processing.
- Ready for Delivery.
- Out for Delivery.
- Delivered.
- Completed.
- Cancelled.
- Expired.
- Delivery Failed.
- Refund Pending.
- Refunded.

All status transitions must be validated by backend business rules.

Implement:

- Secure authentication.

- Role-based access control.

- API request validation.
- Webhook signature verification where supported.
- Rate limiting.
- Input sanitization.
- Secure secret management.
- Audit logs.
- Session management.
- Protection against unauthorized data access.

Create different permission levels for:

**Owner**
- Full business access.
- Manage administrators.
- Configure system settings.
- View financial reports.
- Manage products, inventory, and orders.

**Manager**
- Manage products.
- Manage inventory.
- Manage orders.
- View permitted reports.

**Staff**
- Access assigned operational functions.
- View and update permitted orders.
- Perform authorized inventory operations.

**Customer**
- Access personal shopping information.
- Manage personal cart.
- Place and view personal orders.

A user must never be able to access another customer's private information through AI tool manipulation or direct API requests.

# 10. Infrastructure and Deployment

The application must be designed to run on an Ubuntu VPS with approximately 1 GB RAM.

Resource efficiency is a major architectural requirement.

Use:

- Ubuntu Server.
- Nginx.
- FastAPI.
- Uvicorn.
- PostgreSQL.
- External AI model API.
- Meta WhatsApp Cloud API.

Deployment principles:

1. Serve the compiled React frontend as static files through Nginx.
2. Run FastAPI with a conservative worker configuration.
3. Use PostgreSQL with memory settings appropriate for the VPS.
4. Avoid unnecessary background processes.
5. Avoid running local AI models.
6. Avoid Kubernetes and microservices.
7. Avoid Redis unless a demonstrated requirement justifies it.
8. Use asynchronous processing only where it provides meaningful benefits.
9. Monitor memory, CPU, disk, API latency, and application errors.
10. Account for monitoring software when calculating available memory.

Docker Compose may be used if its resource overhead is acceptable.

Include:
- Environment configuration.
- Database migrations.
- Automated backups.
- Application logging.
- Health checks.
- HTTPS.
- Deployment documentation.
- Recovery procedures.

# 14. Quality and Acceptance Criteria

The platform is considered functionally complete when:

- Customers can interact with the shop through WhatsApp.
- Customers can search products and receive accurate recommendations.
- Customers can manage carts and place orders.
- Administrators can manage the shop through a web dashboard.
- Administrators can also manage the shop through WhatsApp.
- Both administration interfaces use the same backend and database.
- One AI agent handles both customer and administrator contexts.
- Tool execution is permission-aware.
- Sensitive actions require confirmation.
- Stock quantities remain consistent.
- Order and payment statuses are independently tracked.
- Unauthorized users cannot execute administrative operations.
- AI API usage and costs can be monitored.
- The application can operate within the constraints of a low-memory VPS.

### Final Development Instruction

Before implementing the platform, examine the complete requirements and produce a technical implementation plan.

Define the system architecture, database relationships, API contracts, module responsibilities, AI agent workflow, security boundaries, and deployment strategy.

Identify dependencies and architectural risks before writing code.

Implement the platform using clean, modular, maintainable code. Do not introduce unnecessary technologies or infrastructure.

Prioritize correctness, security, low resource consumption, and a consistent user experience.

Do not use mock functionality as a substitute for real integrations in production. Clearly distinguish working integrations from development placeholders.

Build a complete, integrated platform rather than a collection of disconnected demonstration pages.
